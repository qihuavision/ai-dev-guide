# 立项与需求：立项书与 PRD 怎么写

> 本篇是 [`01-AI协作开发方法论.md`](01-AI协作开发方法论.md) 第一步、第二步的展开。
> 适用于任何类型的项目（工具、Web、服务、脚本）。把"做什么"和"不做什么"在写代码之前定义死，是 AI 协作开发成败的分水岭。

---

## 0. 为什么立项和需求这一步最重要

AI 协作开发最大的失败模式不是"AI 写不出代码"，而是 **"范围蔓延 + 上下文丢失"**。这两者的根都在立项和需求阶段：

- 立项书没写"不做什么" → AI 不知道边界，越写越大
- PRD 没拆到功能点 → AI 一次想做完整个系统，必然失控
- 目标不可衡量 → 验收时说不清"做完了没有"

> 💡 **核心原则：先把边界画死，再往里填东西。** 护栏比方向更重要。

---

## 1. 立项书（Charter）的 6 个必要部分

不要直接对 AI 说"帮我写个 XX 工具"。要先用一份立项书把项目定义死，这是整个项目的"宪法"。

📋 模板：[`../templates/00-立项书.md`](../templates/00-立项书.md)

### 1.1 背景与痛点

写清楚"为什么要做这个项目"。必须包含：

- **现状描述**：现在是怎么做的？2-3 个具体场景（不是抽象的"效率低"）
- **量化痛点**：能用数字说话就用数字（耗时、频次、出错率、人力成本）

| 写法 | 评价 |
|---|---|
| ❌ "现在效率很低，需要优化" | 抽象，无法验收 |
| ✅ "现在每天人工跑 20 条巡检 SQL，每条平均 3 分钟，慢查询靠人肉看日志" | 具体场景 + 量化 |

> ⚠️ 如果背景写不出 2 个具体场景，说明你还没想清楚到底解决什么问题，**先别立项**。

### 1.2 目标（SMART）

目标必须满足 SMART 原则：**S**pecific（具体）、**M**easurable（可衡量）、**A**chievable（可实现）、**R**elevant（相关）、**T**ime-bound（有时限）。

详见 [§3 SMART 目标的写法示例](#3-smart-目标的写法示例)。

### 1.3 范围（做 / 不做）

这是立项书里**最重要**的一节，详见 [§2 "不做什么"为什么最重要](#2-不做什么为什么最重要)。

### 1.4 用户与角色

- **主用户**：谁天天用？什么场景下用？
- **次用户**：谁偶尔用？（管理员、审计人员、访客）
- **权限分级**：谁能看、谁能改、谁能执行危险操作

> 💡 写清楚角色，后面做权限设计、写测试用例都有依据。AI 知道有几类用户，就不会漏掉权限分支。

### 1.5 技术约束（红线）

把不可协商的技术边界写死，避免 AI 自作主张选型：

- 语言 / 框架 / 运行时版本
- 部署环境（容器 / 裸机 / Serverless / 浏览器）
- 依赖限制（不能用某类库、必须用某类库）
- 兼容性要求（操作系统、浏览器、协议版本）
- 红线（绝不能碰的东西，如"不能引入付费 API"、"不能写入生产库"）

### 1.6 成功标准

用**可勾选**的方式写，验收时逐项打勾：

- [ ] 标准 1（可衡量、可验证）
- [ ] 标准 2
- [ ] ...

> 🎯 检验标准：把这一节发给一个没参与项目的人，他能客观判断"做到了 / 没做到"，就算合格。如果他说"看情况"，说明标准不够客观。

## 2. "不做什么"为什么最重要

**明确"不做什么"比"做什么"更重要。** 这是本库反复强调的核心理念。

### 2.1 为什么 AI 协作项目必须写"不做什么"

AI 协作项目失败 **80% 是因为"范围蔓延"**。AI 的默认行为是"帮你把事情做完整"，于是：

- 你说"加个导出功能" → AI 顺手加了导出 + 邮件发送 + 定时任务 + 三种格式
- 你说"做个登录" → AI 顺手做了注册 + 找回密码 + OAuth + 角色管理
- 下次会话，AI 又设计了另一种风格的角色管理，和上次冲突

**"不做什么"就是给 AI 画的护栏。** 没有护栏，AI 会一路狂奔到失控。

### 2.2 "不做什么"的三种来源

每一条都要写明**为什么不做**，否则会被后人无视：

| 来源 | 示例 |
|---|---|
| **已有替代方案** | "不做监控告警，已有 Prometheus" |
| **本期不做（推到下期）** | "不做多租户，本期单组织" |
| **永远不做（违背定位）** | "不做图形界面，定位是 CLI 工具" |

### 2.3 怎么用"不做什么"挡住范围蔓延

在 PRD 里、在交接文档里、在每次会话的开场白里，**都要重复一遍"不做什么"**。当 AI 提议加某个功能时，对照这一节：在范围内吗？不在就明确拒绝，并让 AI 把它记到"待办池（未来想法，现在不做）"，而不是顺手实现。

## 3. SMART 目标的写法示例

SMART = Specific / Measurable / Achievable / Relevant / Time-bound。

### 3.1 反面教材 vs 正面教材

| 维度 | ❌ 反面（不 SMART） | ✅ 正面（SMART） |
|---|---|---|
| 具体 | "提升效率" | "把日常巡检从人工 60 分钟降到工具自动 5 分钟" |
| 可衡量 | "做得更好用" | "覆盖 20 条核心巡检项，一键生成报告" |
| 可实现 | "完全自动化一切" | "自动化 80% 的常规巡检，剩余 20% 需人工判断" |
| 相关 | （和痛点无关的目标） | 直接对应背景里列出的痛点 |
| 有时限 | "尽快完成" | "4 个 Sprint 内（约 8 周）交付 v1.0" |

### 3.2 SMART 目标模板

```
在 [时限] 内，实现 [具体功能/能力]，
达到 [可衡量的指标]，
解决 [背景里的痛点]。
```

示例（占位符，项目无关）：

> 在 8 周内（4 个 Sprint），实现覆盖 20 项核心检查的自动化巡检工具，
> 达到"一键执行 + 5 分钟出报告"的指标，
> 解决"现在人工跑 60 分钟、易遗漏"的痛点。

> 💡 一个项目最多 3-5 个 SMART 目标。多了等于没目标。

## 4. PRD 怎么拆到功能点级别

立项书是"为什么"，PRD 是"做什么"。PRD 的核心任务是把项目拆到 **AI 一次会话能完成一个** 的粒度——也就是功能点级别。

📋 模板：[`../templates/01-PRD.md`](../templates/01-PRD.md)

### 4.1 拆解原则

| 拆得太大（❌） | 拆得刚好（✅） |
|---|---|
| "用户管理模块" | "功能点：用户注册" |
| "导出功能" | "功能点：导出当前列表为 CSV" |
| "权限系统" | "功能点：基于角色的接口访问控制" |

**判断标准：一个功能点能不能在一次 AI 会话内完成、跑通测试、commit？** 能，就是合适的粒度。

### 4.2 拆解步骤

1. **列功能模块**：从立项书的目标反推需要哪几大块能力
2. **每个模块拆功能点**：按"用户能做的每一个独立动作"拆
3. **每个功能点写卡片**（见 [§5](#5-功能点卡片的-6-个要素)）
4. **排优先级**（见 [§6](#6-功能优先级矩阵)）
5. **每个功能点都要有"不做"**（护栏）

### 4.3 PRD 的结构

一份合格的 PRD 至少包含：

- 概述（一句话 + 对应立项书的哪个目标）
- 名词表（领域术语统一，避免 AI 用不同词指代同一概念）
- 功能点列表（每个一张卡片）
- 非功能需求（性能、安全、可访问性等）
- 功能优先级矩阵

> ⚠️ 名词表经常被忽略，但极其重要。AI 在不同会话里可能把同一个东西叫"任务""作业""Job"，导致代码命名混乱。在 PRD 里钉死术语。

## 5. 功能点卡片的 6 个要素

每个功能点都要写清楚这 6 块。这是给 AI 的"作业说明书"——少了任何一块，AI 都会自己脑补，而脑补往往就是 bug 的来源。

```
触发方式 / 输入 / 处理逻辑 / 输出 / 异常处理 / 不做
```

### 5.1 触发方式（When）

功能在什么条件下被唤起？

- 用户主动操作（点按钮、敲命令、调接口）
- 系统事件（定时、消息到达、状态变化）
- 外部调用（API、Webhook）

> 明确触发方式，AI 才知道这个功能的"入口"在哪里，该挂到哪个路由 / 命令 / 事件上。

### 5.2 输入（Input）

功能接收什么？

- 字段名、类型、是否必填、取值范围
- 来源（用户输入 / 配置 / 上游接口 / 数据库）
- 示例值（占位符即可）

> 💡 输入要写到"字段级"。只写"接收用户信息"是不够的，AI 会自己编字段。

### 5.3 处理逻辑（Process）

拿到输入后做什么？用**步骤化、可验证**的方式描述：

1. 第一步：校验输入（校验规则）
2. 第二步：查询 / 计算（核心逻辑）
3. 第三步：副作用（写入、通知、调用外部）
4. ...

> ⚠️ 不要写"智能地处理"这种模糊词。每一步都要能对应到代码里的一个函数。模糊的地方就是 AI 自由发挥（也就是失控）的地方。

### 5.4 输出（Output）

功能产出什么？

- 返回值结构（字段、类型）
- 呈现形式（控制台输出 / HTTP 响应 / 文件 / UI 变化）
- 成功和失败分别长什么样

### 5.5 异常处理（Error Handling）

最容易漏的一块。必须覆盖：

- 输入非法怎么办？
- 依赖（数据库、外部 API、文件）不可用怎么办？
- 权限不足怎么办？
- 超时 / 部分失败怎么办？

> 🎯 原则：**每个异常都要有明确的处理策略**（报错 / 重试 / 降级 / 回滚），不能让 AI 自己决定"大概 throw 一下就行"。

### 5.6 不做（Out of Scope）

这个功能点**不包含**什么？和立项书的"不做什么"一脉相承，但更细粒度。

示例（占位符）：

- 本功能点不做分页（分页是另一个功能点）
- 本功能点不做缓存（性能优化阶段统一做）
- 本功能点不做权限校验（由中间件统一处理）

> 💡 **每个功能点都要写"不做"。** 这是阻止 AI 顺手加戏的最有效手段。

## 6. 功能优先级矩阵

排开发顺序时，不要只看"业务优先级"。建议画一张三维表：**优先级 × 难度 × 危险等级**。

### 6.1 危险等级（最重要）

**原则：先做安全的功能，架构稳了再碰危险操作。**

| 危险等级 | 含义 | 建议 |
|---|---|---|
| 🟢 安全 | 只读、无副作用、可随时重跑 | **优先做**，用来搭骨架、验证架构 |
| 🟡 中 | 在隔离环境有写操作（写文件、写测试库） | 架构稳定后做，必须能回滚 |
| 🔴 危险 | 碰生产 / 不可逆 / 涉及金钱或数据销毁 | **最后做**，必须人工确认 + Dry-run |

### 6.2 优先级（业务价值）

| 优先级 | 含义 |
|---|---|
| P0 | 没它项目没法交付（核心路径） |
| P1 | 重要，但能先上线再补 |
| P2 | 锦上添花，待办池 |

### 6.3 难度（实现成本）

| 难度 | 含义 |
|---|---|
| S | 半天内能搞定 |
| M | 1-2 天 |
| L | 一周以上，可能要拆成多个功能点 |

### 6.4 排序建议

推荐的推进顺序：

1. **P0 + 🟢 + S/M**：先把核心只读路径打通，端到端跑通一条命令（Sprint 1 的可运行里程碑）
2. **P0 + 🟡**：补上必要的写操作（隔离环境）
3. **P1**：辅助功能
4. **P0 + 🔴**：最后才碰危险操作，且必须有审批流和 Dry-run

> ⚠️ 反面教材：一上来就做 🔴 危险功能。架构还没稳，AI 写的删除/写入逻辑一旦有 bug，后果不可逆。

### 6.5 矩阵表格示例（占位符）

| 功能点 | 优先级 | 难度 | 危险 | 排序 |
|---|---|---|---|---|
| 功能点 A（只读查询） | P0 | S | 🟢 | 1 |
| 功能点 B（写隔离环境） | P0 | M | 🟡 | 2 |
| 功能点 C（导出报告） | P1 | S | 🟢 | 3 |
| 功能点 D（生产写操作） | P0 | L | 🔴 | 最后 |

## 7. 小结与检查清单

立项与需求阶段做完后，逐项打勾：

- [ ] 立项书写完，含 6 个部分（背景/目标/范围/角色/约束/成功标准）
- [ ] "不做什么"已明确，且每条写了原因
- [ ] 目标是 SMART 的（具体、可衡量、有时限）
- [ ] PRD 拆到功能点级别（每个能一次会话完成）
- [ ] 每个功能点写了 6 要素卡片（触发/输入/处理/输出/异常/不做）
- [ ] 功能优先级矩阵已排（优先级 × 难度 × 危险）
- [ ] 危险操作（🔴）排在最后，且有 Dry-run + 人工确认

> 🎯 **验收标准**：把立项书和 PRD 发给一个完全没参与过项目的 AI，让它复述"这个项目做什么、不做什么、先做哪个功能"，如果它答得和你预期一致，需求阶段就合格了。
