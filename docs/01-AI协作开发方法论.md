# AI 协作开发方法论

> 这是本库的核心文档。任何项目开工前，让 AI 先完整读一遍本文件。
> 它覆盖"立项 → 需求 → 架构 → 开发 → 交接 → 验收"全流程，适用于任何类型的项目（工具、Web、服务、脚本）。

---

## 第零步：开工前的三个"灵魂问题"

让 AI 写一行代码之前，必须能用一句话回答下面三个问题。**答不上来就不要立项：**

| 问题 | 回答模板 | 示例 |
|---|---|---|
| **给谁用？** | 角色 + 使用场景 | "给运维 + 组内 3 人，日常巡检和应急处理用" |
| **解决什么痛点？** | 现在怎么做、有多痛 | "现在每天手动跑 20 条 SQL 巡检，慢查询靠人肉看" |
| **不做什么？（最重要）** | 明确排除项 | "不做监控告警（已有 Prometheus），不做 HA（有 Orchestrator）" |

> ⚠️ 第三个问题最关键。AI 协作项目失败 **80% 是因为"范围蔓延"** —— AI 不知道边界，就会越写越大，最后失控。**明确"不做什么"比"做什么"更重要。**

---

## 第一步：立项文档（让 AI 准确理解项目）

不要直接对 AI 说"帮我写个 XX 工具"。要先用一份**立项书（Charter）**把项目定义死。

📋 模板：[`templates/00-立项书.md`](../templates/00-立项书.md)

立项书必须包含 6 个部分：
1. **背景与痛点**（现状 2-3 个具体场景 + 量化痛点）
2. **目标（SMART）**（具体、可衡量、有时限）
3. **范围**（做 In Scope / 不做 Out of Scope —— 护栏）
4. **用户与角色**（主用户 / 次用户 / 权限）
5. **技术约束**（语言、部署、依赖版本、红线）
6. **成功标准**（可验收的勾选项）

> 💡 把立项书存成 `docs/00-立项书.md`，这是整个项目的"宪法"，每次开新会话都先让 AI 读它。

---

## 第二步：需求文档（PRD）—— 把"做什么"拆到 AI 能执行

立项书是"为什么"，PRD 是"做什么"。PRD 要拆到**功能点级别**，每个功能点要有输入 / 输出 / 异常 / 不做。

📋 模板：[`templates/01-PRD.md`](../templates/01-PRD.md)

### 功能点卡片格式

每个功能点都要写清楚这 6 块：

```
触发方式 / 输入 / 处理逻辑 / 输出 / 异常处理 / 不做
```

> 💡 **关键技巧：每个功能点都要写"不做"**。这是给 AI 画的护栏。

### 功能优先级矩阵

排开发顺序时，建议画一张表：**优先级 × 难度 × 危险等级**。

原则：**先做安全的功能，架构稳了再碰危险操作。**

| 危险等级 | 含义 | 建议 |
|---|---|---|
| 🟢 安全 | 只读、无副作用 | 优先做 |
| 🟡 中 | 在隔离环境有写操作 | 架构稳定后做 |
| 🔴 危险 | 碰生产 / 不可逆 | 最后做，必须人工确认 |

## 第三步：架构设计（写代码前定死）

让 AI 写代码前，先让它产出设计文档，你审核通过后再写代码。**否则 AI 每次会话都会重新设计架构，导致代码风格不一致。**

📋 模板：[`templates/02-架构设计.md`](../templates/02-架构设计.md)

### 三份必出的设计文档

1. **架构设计文档**：模块职责、调用关系、依赖图
2. **数据/存储设计文档**：项目自己的元数据 / 配置 / 历史记录怎么存
3. **安全设计文档**（涉及数据/权限/网络的项目必备）

### 推荐：用 ADR 记录关键决策

重大技术决策用 **ADR（Architecture Decision Record）** 记录下来：

```
### ADR-XX：决策标题
- 背景：为什么要做这个决策
- 决策：选了什么
- 备选：还考虑过什么
- 后果：这个决策带来的影响
```

> 💡 ADR 放在交接文档或单独的 `docs/decisions/` 目录。新 AI 会话看 ADR 就能理解"为什么这么设计"，避免它推翻已有决策。

## 第四步：AI 协作开发工作流（怎么"开写"）

这是核心。AI 开发和传统开发的根本区别：**AI 的上下文是有限的，必须分批、可验证地推进。**

### 4.1 黄金四法则

1. **一次一个功能点**：不要一次让 AI 写整个模块。每次只写一个功能。
2. **测试先行**：先让 AI 写测试用例（基于 PRD 的输入/输出），再写实现。
3. **可运行里程碑**：每完成一个功能点，必须能跑通一条命令。
4. **小步提交**：每个功能点完成后 `git commit` 一次（改坏了能回滚）。

### 4.2 单次会话的标准开场白

每次开新会话，用这个模板（**不要寒暄，直接给上下文**）：

📋 模板：[`templates/ai-session-prompt.md`](../templates/ai-session-prompt.md)

```markdown
你是一位资深 [语言] 工程师，帮我开发 [项目名]。

请先阅读以下文档了解项目背景：
1. docs/00-立项书.md（项目目标和范围）
2. docs/01-PRD.md（需求，重点看"功能点：XXX"这一节）
3. docs/02-架构设计.md（已有的模块划分）
4. docs/99-交接文档.md（当前进度）

本次任务：实现【功能点：XXX】

要求：
1. 先看 tests/ 下对应测试是否存在，不存在则按 PRD 写测试
2. 实现对应模块
3. 注册命令 / 入口
4. 跑通测试后告诉我结果
5. 完成后更新 docs/99-交接文档.md

约束：遵守 docs/02-架构设计.md 的目录结构和命名规范。
```

### 4.3 分阶段交付（Sprint 节奏）

每个 Sprint 必须有**可运行的产出**和**明确的验收标准**，结束后更新交接文档。

| Sprint | 典型目标 | 验收标志 |
|---|---|---|
| Sprint 1 | 骨架 + 最小回路（能连、能跑、能输出） | 一条命令端到端跑通 |
| Sprint 2 | 核心功能（2-3 个主要功能点） | 核心场景全部可用 |
| Sprint 3 | 辅助功能（通知、报告、调度） | 完整闭环 |
| Sprint 4 | 稳定性、文档、打包交付 | 可交付他人使用 |

## 第五步：交接文档（迁移给另一个 AI 的关键）

这是 AI 协作开发**最重要的一份文档**。它让任何新的 AI 会话能在 5 分钟内接手项目。

📋 模板：[`templates/99-交接文档.md`](../templates/99-交接文档.md)

### 交接文档必须包含的 10 项

1. 项目一句话
2. 当前状态（进度 / 最后可运行版本 / 健康度）
3. 已完成功能表（功能 / 文件 / 状态 / 测试）
4. 进行中 / 下一步
5. 关键技术决策（ADR）
6. 已知问题 / 坑
7. 本地运行方式
8. **不要做的事**（给下一个 AI 的警告）
9. 待办池（未来想法，现在不做）
10. 上次会话遗留问题

> 🎯 **交接文档的检验标准**：把它发给一个完全没参与过项目的 AI，让它复述"这个项目现在在做什么、下一步做什么、有什么坑"，**如果它能答对，文档就合格了**。

### 增量更新原则

**不要等写到一半才生成交接文档，而是每次会话结束都增量更新。**

如果已经写了一半才发现没文档，用这个 prompt 补救：

```markdown
请扫描当前项目代码，帮我生成/更新以下文档：
1. 架构现状文档（基于实际代码画模块依赖图，从代码反推职责，不要猜）
2. 交接文档（扫描所有源文件统计完成度、运行测试、从注释和 TODO 提取已知问题）
3. README.md（安装步骤 + 使用示例）
要求：基于代码事实，不要编造。不确定的地方标注 [待确认]。
```

## 第六步：让 AI 帮你"生成落地文档"的技巧

如果你已经写了一半代码才想起来规范，不要慌。让 AI 反向从代码生成文档：

```markdown
请扫描当前项目代码，帮我生成/更新以下文档：
1. **架构现状文档**：
   - 基于实际代码画出模块依赖图（用 mermaid）
   - 列出每个模块的实际职责（从代码反推，不要猜）
2. **交接文档**：
   - 扫描所有源文件，统计已完成/未完成功能
   - 运行测试，记录通过/失败
   - 从代码注释和 TODO 中提取已知问题
3. **README.md**：
   - 安装步骤
   - 使用示例（基于实际命令）
要求：基于代码事实，不要编造。不确定的地方标注 [待确认]。
```

## 第七步：最容易忽略的坑（通用版）

不同类型项目有不同专属坑，但下面这些是**所有项目通用的**：

### 7.1 安全底线（不过关不能上线）

| 项 | 做法 |
|---|---|
| 凭据存储 | 密码 / token / key **绝不能**明文存代码或配置，用环境变量 / Vault / 加密配置 |
| 最小权限 | 工具使用的账号只要完成任务所需的最小权限，绝不滥用 root / admin |
| Dry-run 模式 | 任何有副作用的操作，默认 `--dry-run`，先打印不执行 |
| 操作白名单 | 维护"允许执行的操作"白名单，不在白名单的一律拒绝 |
| 审计日志 | 工具执行的每个重要操作都要落日志（who / when / what / result） |
| 审批流 | 危险操作必须人工确认，不能全自动 |
| 网络隔离 | 涉及生产环境的，工具能访问生产，但生产不能反向访问工具 |

📋 详见：[`checklists/安全检查清单.md`](../checklists/安全检查清单.md)

### 7.2 可观测性

工具自己也要被监控：
- 任务执行成功率
- 任务耗时趋势
- 异常告警（**工具挂了谁发现？**）

### 7.3 测试策略（AI 时代特别重要）

```
tests/
├── unit/              # 纯逻辑测试，mock 掉外部依赖
├── integration/       # 真实环境集成测试
├── fixtures/          # 测试用的样本数据
└── golden/            # 金标准输出（回归测试，防止 AI 改坏）
```

> 重点：准备一份"金标准"测试数据，每次 AI 改代码后跑回归，**防止 AI 优化时改坏已有功能**。这是 AI 协作开发特有的坑 —— AI 为了实现新功能，很容易顺手重构掉旧逻辑。

### 7.4 版本与发布

- 语义化版本号（`vMAJOR.MINOR.PATCH`）
- `CHANGELOG.md` 记录每个版本改了啥
- 危险功能用 **feature flag** 控制（默认关闭）
