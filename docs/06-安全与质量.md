# 安全与质量底线

> 本文定义 AI 协作开发中**所有项目通用**的安全与质量底线。无论项目用什么语言、什么框架、面向什么用户，下面这些要求都是不可妥协的下限，不是可选项。

本文档是 AI 协作开发规范库的一部分。安全相关逐项检查表见 [../checklists/安全检查清单.md](../checklists/安全检查清单.md)，交付前检查表见 [../checklists/交付检查清单.md](../checklists/交付检查清单.md)。

---

## 1. 安全底线

安全不是「上线前再加」的功能，而是从第一行代码就要遵守的约束。AI 生成代码时尤其要盯紧这一块——它会写出「能跑但危险」的代码。

### 1.1 凭据存储

**原则：密钥、令牌、密码、连接串永远不进代码仓库。**

- 所有凭据通过**运行时注入**获取：环境变量、秘密管理服务（如 Vault、AWS Secrets Manager、云厂商 KMS）、本地 `.env`（且 `.env` 必须在 `.gitignore` 里）。
- 代码里只能出现**变量名引用**（如 `process.env.DB_PASSWORD`、`os.getenv("API_KEY")`），永远不出现明文值。
- 提供一个 `.env.example` 模板，列出需要哪些变量，但值留空或填假数据。
- **CI/CD 里的凭据同样如此**：用平台的 secret 管理（GitHub Secrets、GitLab CI Variables），不要硬编码到 workflow 文件里。
- 提交前用 secret 扫描工具检查（如 `gitleaks`、`trufflehog`），防止 AI 把测试用的真实 token 顺手提交。

> AI 协作高风险点：AI 经常为了「让 demo 跑起来」直接把 API key 写进源码。任何 PR 里出现疑似凭据的字符串，必须 block。

### 1.2 最小权限

**原则：任何组件、任何进程、任何令牌，只授予完成其职责所需的最小权限。**

- 数据库账号按角色拆分：应用运行用一个账号（只能 CRUD 业务表），迁移用另一个账号（有 DDL 权限）。不要让运行时账号当 superuser。
- 云资源 IAM 策略按「能做什么、能访问哪些资源」精确限定，禁止使用 `*:*` 这类通配宽授权。
- 第三方 API 令牌按需申请 scope，用不到的权限不要勾选。
- 文件系统权限：服务进程只对它需要的目录有读写权，其他只读或不可见。
- 容器以非 root 用户运行。

### 1.3 Dry-run（演练模式）

**原则：任何有破坏性副作用的操作（删除、覆盖、批量修改、发邮件、扣款、调用付费 API），必须先有一个 dry-run 模式。**

- 默认或通过 `--dry-run` 开关，操作只打印「将要做什么」，不真正执行。
- 批量操作必须显示「将影响 N 条记录，预览前 10 条」，由人确认后再真跑。
- 不可逆操作（删表、清空队列、发送对外通知）必须有**二次确认**，且确认信息里包含影响范围。
- AI 生成的迁移脚本、清理脚本，默认先 dry-run，禁止上来就执行。

### 1.4 白名单

**原则：对外部输入的接受范围采用「显式允许」而非「显式拒绝」。**

- 文件上传：按 MIME 类型 + 文件头魔数双重校验，只允许白名单格式，不要维护一个「禁止列表」（永远列不全）。
- 命令/指令路由：只接受预定义的命令集合，未知输入直接拒绝，不要做「模糊匹配」。
- 网络出口：服务只能访问白名单域名（egress allowlist），防止被注入后外发数据。
- AI 工具能调用的外部能力（API、shell 命令、文件路径）必须是白名单内的，不允许任意执行。
- SQL 查询、模板渲染：用户输入只能作为**数据**传入参数化查询/转义管道，永远不能拼进**代码**层。

### 1.5 审计日志

**原则：所有敏感操作必须留痕，且日志本身不可被普通用户篡改。**

- 必须记录的操作：登录/鉴权事件、权限变更、数据导出、批量删除、配置修改、付费操作、AI 工具的调用（输入摘要 + 输出摘要 + 调用者）。
- 每条日志至少包含：时间戳、操作者标识、操作类型、目标对象、结果（成功/失败）、来源 IP 或调用链 ID。
- 日志写到**独立的、只追加**的存储，应用进程无删除权限。
- 日志里**绝不**出现明文凭据、敏感个人信息（密码、卡号、身份证号），敏感字段要脱敏。

### 1.6 审批流

**原则：高风险变更必须经过人或机制的二次确认，不能由单一主体（尤其不能由 AI 单独）拍板。**

- 生产环境部署、数据库 schema 变更、安全组/防火墙修改、删除生产数据：必须有人工审批环节。
- 审批与执行**职责分离**：提 PR 的人和 merge 的人不能是同一个（至少在关键仓库/关键路径上）。
- AI 提出的高风险操作（删数据、改架构、引入新依赖）必须由人 review 后才执行，AI 不能自动跑这类操作。
- 紧急通道（break-glass）可以存在，但必须事后补审批并记录原因。

### 1.7 网络隔离

**原则：不同信任等级的组件之间必须有边界，默认拒绝跨边界访问。**

- 服务之间按网络分段：公网入口、内部服务、数据层彼此隔离，内部服务不直接暴露公网。
- 数据库、缓存、消息队列等基础设施**不对外网开放**，只接受来自应用层的连接。
- AI 工具/Agent 运行的环境如果需要联网，走受控代理，代理上做域名白名单和流量审计。
- 开发环境与生产环境物理或逻辑隔离，开发环境用的凭据在生产环境无效。

## 2. 测试策略：四层测试结构

测试不是「写完功能补一下」，而是 AI 协作里**防止 AI 改坏已有功能**的第一道防线。推荐四层结构，从快到慢、从细到粗：

| 层级 | 测什么 | 范围 | 速度 | 运行频率 |
|------|--------|------|------|----------|
| Unit | 单个函数/模块的逻辑 | 一个函数 | 毫秒级 | 每次保存 |
| Integration | 多个组件协作 | 一个子系统 | 秒级 | 每次 commit |
| Fixtures | 真实输入下的端到端行为 | 完整链路 | 秒~分钟级 | 每次 PR |
| Golden | 关键输入→期望输出 的固化对比 | 关键路径 | 取决于输入 | 每次 PR + 每次 AI 重构 |

### 2.1 Unit 测试

- 测单个函数的纯逻辑，所有外部依赖 mock 掉。
- 覆盖正常路径、边界值、空输入、非法输入。
- 一个测试只断言一件事，失败信息要能直接定位问题。
- 目标是**快**：整个 unit 套件应该在几秒内跑完，让开发者愿意频繁跑。

### 2.2 Integration 测试

- 测多个组件组装后的行为，例如「服务 + 真实数据库（测试库）」「API 端到端」。
- 用真实依赖的测试实例（测试数据库、内存队列），而不是全 mock，否则集成意义不大。
- 覆盖组件间的契约：接口字段、错误传播、事务边界。

### 2.3 Fixtures 测试

- 用一组**固定的、有代表性的真实输入**跑完整流程，断言关键结果。
- Fixtures 进版本库，作为「项目历史输入的快照」长期保留。
- 每次遇到线上 bug，把触发 bug 的输入加成一条 fixture（先写一条失败的 fixture 复现 bug，再修复）。

### 2.4 Golden 测试（金标准测试）——AI 时代的重中之重

**Golden 测试 = 把一组关键输入的「当前正确输出」固化下来作为基准，未来任何改动如果让输出偏离基准，测试就失败。**

#### 为什么 Golden 测试在 AI 时代特别重要

1. **AI 改代码时，最容易坏的是「没人盯着的那部分既有行为」**。AI 重构一个函数，单元测试可能还过（因为它只测了函数本身），但函数下游的输出格式、文案、顺序已经悄悄变了。Golden 测试就是来抓这种回归的。
2. **AI 擅长「让测试通过」，但不擅长「判断输出对不对」**。如果你只写「输出不为空」「状态码 200」这种弱断言，AI 很容易给出一个「技术上通过、语义上错误」的结果。Golden 测试把期望输出锁死，AI 没法糊弄。
3. **它是「行为契约」的具象化**。Golden 数据本身就是文档——任何人（人或 AI）看一眼 golden 输入输出对，就知道这个功能该是什么样。
4. **重构时的安全网**。有了 golden 测试，你才敢让 AI 大刀阔斧重构，因为任何行为偏移都会立刻报警。

#### Golden 测试怎么写

```
对每一个关键功能路径：
  1. 选 3~10 个有代表性的输入（正常、边界、异常各覆盖）
  2. 用当前「已验证正确」的版本跑一遍，把输出存成 golden 文件
  3. 测试代码：读输入 → 跑逻辑 → 拿输出 → 与 golden 文件 diff
  4. diff 不为空 → 测试失败，并打印差异
```

- 输出中**不要包含易变字段**（时间戳、随机 ID、路径），要么固定、要么在比较前归一化。
- Golden 文件进版本库，任何 golden 文件的变更必须在 PR 里说明「为什么期望输出变了」。
- 提供「更新 golden」的命令（如 `--update-golden`），但**只能由人显式触发**，不能在普通测试运行时自动覆盖。

## 3. 金标准测试数据的准备方法

Golden 测试的质量取决于测试数据的质量。坏数据会让 golden 测试要么形同虚设，要么频繁误报。

### 3.1 数据来源

- **真实脱敏数据**：从生产环境采样，严格脱敏（替换 PII、打乱 ID、移除敏感字段），获得最接近真实分布的输入。这是首选。
- **合成数据**：用脚本按已知规则生成，覆盖边界和异常场景。适合真实数据不足或合规不允许时。
- **历史 bug 样本**：每次线上 bug 修复后，把触发输入沉淀成一条 golden 数据。这是最有价值的一类，因为它代表「真实出过事」的路径。

### 3.2 数据集构成原则

- **覆盖度优先于数量**。10 条精心挑选的输入（覆盖所有分支）比 1000 条随机输入更有用。
- 必须包含的三类：
  - **典型正常输入**：验证主路径行为稳定。
  - **边界与异常输入**：空值、超长、特殊字符、非法格式、并发场景。
  - **历史回归输入**：来自过往 bug 的样本。
- 每条数据都带一行注释说明「这条数据是为了验证什么」。

### 3.3 数据管理

- 测试数据集中存放在固定目录（如 `tests/fixtures/`、`tests/golden/`），不要散落各处。
- 大文件用外部存储或 LFS，不要把几十 MB 的 fixture 直接塞进 git 污染历史。
- 数据要有版本：当输入 schema 变了，老数据要能对应到老版本的行为预期，而不是被悄悄改坏。
- 定期 review：删掉冗余数据，补上新发现的风险路径。

## 4. 可观测性：工具自己也要被监控

在 AI 协作场景里，「工具」不仅指应用本身，还包括 AI 调用的各种自动化脚本、命令、Agent。它们同样需要被监控，否则坏了你不知道。

### 4.1 必须采集的指标

- **成功率**：每个工具/接口调用，成功次数 / 总次数。成功率下降往往是第一个故障信号。
- **耗时分布**：p50 / p95 / p99 延迟，不要只看平均值（平均值会被长尾掩盖）。
- **错误分类**：按错误类型、错误来源、调用者维度聚合，定位「哪类调用最容易出问题」。
- **AI 专项指标**：模型调用的 token 消耗、每次会话的工具调用次数、工具被拒绝/超时的次数、人介入修正的频率（反映 AI 自主完成度）。

### 4.2 告警

- 告警基于**症状**（用户能感知到的故障），而不是基于**原因**（某个 CPU 高了）。原因类指标进 dashboard，症状类指标进告警。
- 告警要带**可执行的上下文**：发生了什么、影响范围、去哪看日志、第一步该查什么。裸的「成功率 95%」告警没用。
- 设告警阈值时考虑噪声：宁可少而准，不要多而全。一个天天误报的告警等于没有告警。

### 4.3 日志与追踪

- 结构化日志（JSON），带 request id / trace id，能串起一次请求经过的所有节点。
- 日志分级：DEBUG（默认关）/ INFO / WARN / ERROR，生产默认 INFO 及以上。
- 分布式追踪覆盖所有跨服务调用，能看到「一次请求在哪个环节慢」。

## 5. 版本与发布

### 5.1 语义化版本（Semantic Versioning）

版本号 `MAJOR.MINOR.PATCH`：

- **MAJOR**：不兼容的 API 变更（破坏性）。
- **MINOR**：向后兼容的新功能。
- **PATCH**：向后兼容的 bug 修复。

- 0.x.x 阶段表示「API 还不稳定」，任何版本都可能 breaking，要在文档里明确告知。
- 一旦发布 1.0.0，就要对兼容性负责，任何 breaking change 必须升 MAJOR 并在 CHANGELOG 里高亮。
- AI 生成的「顺手改个接口签名」经常是隐藏的 breaking change，review 时要特别盯。

### 5.2 CHANGELOG

- 维护一份人类可读的变更日志（推荐 [Keep a Changelog](https://keepachangelog.com/) 格式）。
- 按 `Added / Changed / Deprecated / Removed / Fixed / Security` 分类。
- 每次发布打 tag 时，CHANGELOG 对应一段必须更新。
- **Security 一类即使影响很小也要单独列出**，不要混在 Fixed 里。

### 5.3 Feature Flag（功能开关）

- 新功能用 flag 包裹，默认关闭，可独立于发布上线。
- 好处：
  - 解耦「代码合并」和「功能上线」——大功能可以分多次 PR 合并但暂不启用。
  - 出问题可以秒级关闭，不用回滚发布。
  - 可以灰度：先给小流量/内部账号开启，验证后再全量。
- 注意 flag 的生命周期：上线并稳定后的 flag 要及时拆除，否则代码里会堆满死分支。
- AI 友好提示：在交接文档里记录当前有哪些 flag 处于「已合并未启用」状态，避免新会话误以为功能已经生效。

## 6. 质量底线

### 6.1 代码审查 Checklist

每个 PR 至少检查以下项（完整版见 [../checklists/交付检查清单.md](../checklists/交付检查清单.md)）：

- [ ] 功能是否真的解决了问题，而不是「看起来在解决」？
- [ ] 有没有引入已知的安全风险（注入、越权、明文凭据、不安全反序列化）？
- [ ] 是否有对应的测试，且测试覆盖了边界和异常？
- [ ] 是否有 Golden 测试覆盖关键行为（如果改动触及关键路径）？
- [ ] 命名是否清晰到不需要注释也能看懂？
- [ ] 是否引入了不必要的新依赖？依赖是否可信、是否有已知漏洞？
- [ ] 是否破坏了既有 API 或数据兼容性？如果是，是否走了正确的版本/迁移流程？
- [ ] 日志和错误信息是否对排查问题有帮助，且不含敏感信息？
- [ ] 是否删除了调试代码、注释掉的死代码、TODO（或 TODO 带了 issue 链接）？

### 6.2 错误处理

- **错误必须被显式处理，不要吞**。空 catch、静默失败是最常见的隐患。
- **错误要带上下文**：抛错时附带「在做什么、用什么参数、预期是什么」，便于定位。
- **区分业务异常和系统异常**：业务异常（如「余额不足」）走正常返回路径，带用户可读信息；系统异常（如「数据库连不上」）走错误通道，带技术细节给运维。
- **失败要可恢复或可重试**：对瞬时故障（网络抖动）做有限次重试 + 指数退避，不要无限重试放大故障。
- **外部调用要假设它会失败**：超时、断路、降级要有预案，不能让一个下游挂了拖垮整个服务。

### 6.3 日志规范

- **结构化**：JSON 格式，固定字段名，便于采集和查询。
- **分级合理**：生产环境默认 INFO，DEBUG 按需动态开启；ERROR 表示「需要人介入」，不要滥用。
- **一条日志一件事**：不要把一次请求的所有信息塞进一条巨型日志，也不要把一件事拆成十几条找不到关联。用 trace id 串联。
- **脱敏**：日志里永远不出现密码、token、卡号、身份证号等敏感字段，打印对象前先过一遍脱敏。
- **不依赖日志做业务**：日志是观察用的，不能作为业务流程的一部分（比如「靠读日志触发下一步」）。

---

## 7. 小结：三条不可妥协的底线

1. **安全是前置约束，不是后置补丁**。凭据、权限、破坏性操作、外部输入这四块，从第一行代码就要守住。
2. **Golden 测试是 AI 时代的回归防线**。AI 改代码的最大风险是「静默地改坏既有行为」，Golden 测试是唯一能可靠抓住它的手段。
3. **可观测性覆盖工具本身**。AI 调用的每一个脚本、接口、Agent 都要有指标和日志，否则坏了你只能靠用户投诉才知道。
