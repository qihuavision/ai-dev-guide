# AI 会话技巧：怎么和 AI 高效协作

> 本篇是 [`01-AI协作开发方法论.md`](01-AI协作开发方法论.md) 第四步的展开，是整套方法论里**最实操**的一篇。
> 核心论点：AI 的上下文是有限的，必须**分批、可验证**地推进；协作的关键不是"让 AI 写更多代码"，而是"让 AI 在边界内写正确的代码"。

---

## 0. 上下文管理：一切技巧的根基

### 0.1 AI 上下文是有限的

不管 AI 多强大，**单次会话能"记住"的内容有上限**。一旦超过：

- AI 开始"忘记"早期的约束（架构规范、命名约定、"不做什么"）
- AI 开始重复已做过的工作
- AI 的代码风格开始漂移
- 出现幻觉（虚构 API、编造不存在的库）

所以 AI 协作开发的根本工作模式不是"一次写完"，而是 **分批、可验证、可回滚** 的小步推进。

### 0.2 分批可验证推进的三条铁律

1. **一次会话只做一件事**：一个功能点，做完、测过、提交，再开下一个
2. **每个里程碑必须可运行**：每完成一步，要有一条命令能验证"这步成了"
3. **每个功能点结束就 commit**：改坏了能回滚，AI 犯错不会毁掉整个项目

> 💡 把 AI 当成一个"能力很强但记忆很差、容易兴奋的新人"来带：给它明确的任务、明确的边界、明确的验收标准，而不是放手让它自由发挥。

## 1. 黄金四法则

这是 AI 协作开发的四条不可违反的法则。

### 1.1 一次一个功能点

不要一次让 AI 写整个模块。

| ❌ 反面 | ✅ 正面 |
|---|---|
| "帮我把用户管理模块写了" | "实现【功能点：用户注册】，参考 PRD 第 X 节" |
| "把后端全做了" | "实现【功能点：查询列表】，只做只读查询" |

**为什么**：一次做太多，AI 上下文会爆，质量断崖式下降；而且一旦出错，你不知道是哪一步错的，回滚都难。

### 1.2 测试先行

先让 AI 写测试用例（基于 PRD 的输入 / 输出），再写实现。

好处：

- 测试是"需求的具体化"，逼着 AI（和你）先想清楚输入输出
- 实现写完立刻有验证手段
- 后续 AI 改代码时，跑一遍测试就知道有没有改坏（防 AI "顺手重构"）

> ⚠️ 准备一份"金标准"测试数据（`tests/golden/`），每次 AI 改完都跑回归。这是 AI 协作特有的防护——AI 为了加新功能，很容易顺手重构掉旧逻辑。

### 1.3 可运行里程碑

每完成一个功能点，**必须能跑通一条命令**。

- 能编译 / 能启动
- 能跑通对应的测试
- 能执行一次端到端的演示（哪怕只是控制台输出 "OK"）

**为什么**：不可运行的代码等于没写。"差一点就能跑"是最危险的——下次会话接手时，AI 要花大量时间排查"到底哪一步坏了"。

### 1.4 小步提交

每个功能点完成后 `git commit` 一次。

- 改坏了能回滚到上一个好的状态
- 每次提交是一个清晰的"功能增量"，review 容易
- AI 造成的灾难被限制在一个 commit 内

> 💡 提交信息写清楚"实现了哪个功能点"。这样回滚时一眼就知道该回到哪。

## 2. 单次会话开场白模板

每次开新会话，**不要寒暄，直接给上下文**。开场白的质量直接决定这次会话的产出质量。

📋 模板：[`../templates/ai-session-prompt.md`](../templates/ai-session-prompt.md)

### 2.1 标准开场白结构

一个合格的开场白包含四块：**身份 + 背景（读哪些文档）+ 本次任务 + 约束**。

```markdown
你是一位资深 [语言] 工程师，帮我开发 [项目名]。

请先阅读以下文档了解项目背景：
1. docs/00-立项书.md（项目目标、范围、不做什么）
2. docs/01-PRD.md（需求，重点看"功能点：XXX"这一节）
3. docs/02-架构设计.md（模块划分、命名规范、接口约定）
4. docs/99-交接文档.md（当前进度、已知坑、不要做的事）

本次任务：实现【功能点：XXX】

要求：
1. 先看 tests/ 下对应测试是否存在，不存在则按 PRD 写测试
2. 实现对应模块（放到架构文档指定的目录，遵守命名规范）
3. 注册命令 / 入口
4. 跑通测试后告诉我结果
5. 完成后更新 docs/99-交接文档.md

约束：
- 只做这一个功能点，不要顺手加别的
- 遵守 docs/02-架构设计.md 的目录结构和接口约定
- 不确定的标 [待确认]，不要编造
```

### 2.2 开场白的常见错误

| 错误 | 后果 |
|---|---|
| 不让 AI 读文档，直接描述任务 | AI 凭空发挥，不符合已有架构 |
| 一次塞多个功能点 | 上下文爆掉，质量下降 |
| 不写"约束"和"不做" | AI 顺手加戏，范围蔓延 |
| 寒暄 / 客套话 | 浪费上下文，没意义 |

> ⚠️ 最忌讳的开场白："帮我写个 XX，你看着办"。这是把方向盘完全交给 AI，几乎一定会失控。

## 3. 怎么控制 AI 不越界

AI 越界（scope creep）是协作开发最高频的失败模式。控制手段如下。

### 3.1 明确"不做"

在开场白和每个功能点里都写清楚"本次不做 X / Y / Z"。每次 AI 提议加东西，对照"不做"清单：

- 在清单里 → 明确拒绝
- 不在清单里但也不在本次范围 → 记到交接文档的"待办池"，**本次不做**

### 3.2 让 AI 复述需求确认理解

任务开始前，让 AI 先用自己的话复述一遍"本次要做什么、不做什么、验收标准是什么"。

```markdown
开始写代码前，请先用 3 句话复述：
1. 本次要做的是什么功能点
2. 不做什么（边界）
3. 怎么算完成（验收标准）
等我确认后再开始。
```

**为什么有效**：AI 复述的过程会暴露它理解偏差的地方。你趁早纠正，比写完代码再返工省 10 倍力气。

### 3.3 限制单次产出规模

如果 AI 一口气输出了 500 行代码，几乎肯定越界了。控制手段：

- 明确说"只改 X 文件，不要动其他文件"
- 明确说"本次只实现核心逻辑，不做错误处理的边缘情况"
- 如果 AI 输出过长，停下来问它："你是不是超出了本次任务范围？"

### 3.4 让 AI 每步都汇报

```markdown
每完成一步就停下来告诉我，不要一口气做完。
```

分步汇报让你能在每一步检查方向对不对，而不是等一大坨产出后才发现跑偏。

## 4. 怎么让 AI 写出一致的代码

风格一致性是 AI 协作最大的隐性成本。控制手段如下。

### 4.1 让 AI 读已有代码

开始新功能前，让 AI 先读相关模块的已有代码：

```markdown
开始前，先读 src/module_a/ 下的代码，理解已有的：
- 命名风格（驼峰 / 下划线、动词位置）
- 返回值约定（成功 / 失败怎么表示）
- 错误处理方式
新代码必须和已有代码风格一致。
```

### 4.2 遵守架构文档

架构文档（`docs/02-架构设计.md`）里的命名规范、接口约定、目录结构，是风格一致的锚点。每次会话都让 AI 读一遍（开场白里已经包含）。

### 4.3 用 AGENTS.md 让规范自动生效

在项目根放一份 `AGENTS.md`，AI 客户端会自动读取。把"遵循哪些文档、有什么红线、命名规范"写进去，不用每次手动喂。

📋 模板：[`../templates/AGENTS.md`](../templates/AGENTS.md)

### 4.4 提供一个"样板代码"

如果项目里已经有写得规范的模块，告诉 AI："以 `src/module_a/` 为样板，新模块照着这个风格写。" 比抽象描述命名规则有效得多。

### 4.5 Code review 时重点查一致性

AI 改完后，重点检查：

- [ ] 命名是否和已有代码一致
- [ ] 返回值 / 错误处理是否遵循项目约定
- [ ] 文件放对了目录吗
- [ ] 有没有引入和已有模块风格冲突的新依赖

## 5. 常见 AI 协作陷阱

### 5.1 范围蔓延（Scope Creep）

**症状**：你让 AI 加一个功能，它顺手加了三个相关的功能。

**根治**：每个功能点写"不做"，开场白里限制"只做这一个"，AI 提议加戏就拒绝并记到待办池。

### 5.2 过度重构（Over-engineering）

**症状**：你让 AI 改一个小 bug，它把整个模块"顺手优化"了一遍，旧功能被改坏。

**根治**：

- 明确说"只改这一处，不要动其他代码"
- 跑金标准回归测试，发现旧行为变了立刻叫停
- 如果 AI 提议重构，让它单独开一个"重构任务"，不和功能开发混在一起

### 5.3 风格漂移（Style Drift）

**症状**：不同会话产出的代码风格不一（命名、错误处理、目录结构都不同）。

**根治**：架构文档 + AGENTS.md + 让 AI 读已有代码（见 [§4](#4-怎么让-ai-写出一致的代码)）。

### 5.4 幻觉 API（Hallucinated API）

**症状**：AI 调用了根本不存在的库 / 函数 / 方法，代码看着对但跑不起来。

**根治**：

- 让 AI 用到外部依赖时，标注出处（哪个库的哪个版本）
- 不确定的让它标 `[待确认]`，不要编
- 跑测试 + 实际运行验证，幻觉 API 一跑就露馅
- 让 AI 优先用项目已有的依赖，而不是自己引入新的

### 5.5 上下文丢失

**症状**：会话进行到一半，AI 开始"忘记"早期的约束，产出质量下降。

**根治**：见 [§7 什么时候该开新会话](#7-什么时候该开新会话)。

### 5.6 假完成

**症状**：AI 说"已完成"，但实际没跑通、没测过、甚至没编译。

**根治**：

- 永远要求"跑通测试 + 给出实际运行输出"作为完成证据
- 自己亲自跑一遍验收命令
- 让 AI 更新交接文档时写"实际运行结果"，而不是"应该可以"

## 6. 代码审查要点：让 AI 改完后怎么验证

AI 说"做完了"不等于做完了。每次都要走一遍验证流程。

### 6.1 三层验证

| 层次 | 做什么 | 防什么 |
|---|---|---|
| **测试层** | 跑单元 + 集成 + 金标准回归 | 防改坏旧功能、防逻辑错误 |
| **运行层** | 实际执行一次端到端命令 | 防幻觉 API、防"假完成" |
| **代码层** | 看 diff，重点查命名 / 目录 / 越界 | 防风格漂移、防范围蔓延 |

### 6.2 Review diff 的重点清单

- [ ] **范围**：只改了和本次功能点相关的代码吗？有没有顺手改别处？
- [ ] **位置**：新文件放对了目录吗？
- [ ] **命名**：和已有代码风格一致吗？
- [ ] **接口**：返回值 / 错误处理遵循项目约定吗？
- [ ] **依赖**：有没有引入新的、不必要的依赖？有没有幻觉 API？
- [ ] **凭据**：有没有把密码 / token 硬编码进代码或配置？
- [ ] **副作用**：危险操作（写、删、网络）有没有 Dry-run / 确认？
- [ ] **测试**：有没有按 PRD 补测试？测试真的覆盖了输入/输出/异常吗？

### 6.3 让 AI 自检

提交前让 AI 自己跑一遍检查：

```markdown
提交前请自查：
1. 跑通所有测试，贴出结果
2. 确认只改动了和【功能点：XXX】相关的代码
3. 确认没有引入架构文档之外的依赖
4. 确认没有硬编码凭据
5. 更新 docs/99-交接文档.md（完成状态、运行方式、已知问题）
```

> ⚠️ AI 的自检不能替代你的 review，但能过滤掉大部分低级错误。

### 6.4 发现问题怎么让 AI 改

不要含糊地说"这里有问题"。要具体：

```markdown
问题：src/module_a/foo.py 第 42 行，返回值格式和项目约定不一致
（项目约定返回 {ok, data, error}，你直接返回了 data）
要求：改成项目约定的格式，并补一个测试覆盖这个返回结构。
不要动其他代码。
```

具体到**文件 + 行号 + 期望 + 约束**，AI 才能精准修改而不越界。

## 7. 什么时候该开新会话

会话不是越长越好。该开新就开新，否则质量会断崖式下降。

### 7.1 必须开新会话的信号

| 信号 | 含义 |
|---|---|
| **上下文快满了** | AI 开始忘记早期约束，重复已做过的事 |
| **换功能模块** | 新功能和当前会话上下文无关，带着旧上下文反而是噪音 |
| **AI 开始"跑偏"** | 风格漂移、幻觉变多、反复改不对——说明这个会话已经"疲劳" |
| **完成了一个里程碑** | 自然断点，适合 commit + 更新交接文档 + 开新会话 |

### 7.2 开新会话前的收尾动作

**开新会话前，必须做完这三件事**，否则上下文就真的丢了：

1. **`git commit`**：把当前进度固化下来
2. **更新 `docs/99-交接文档.md`**：当前状态、已完成、下一步、已知坑、不要做的事
3. **跑一遍测试**：确认当前版本是健康的，新会话从干净状态开始

> 💡 交接文档就是"会话之间的记忆"。没有它，新会话等于从零开始。详见 [`05-交接文档方法论.md`](05-交接文档方法论.md)。

### 7.3 新会话的开场

用 [§2 的标准开场白](#2-单次会话开场白模板)，让新会话读交接文档 + 架构文档 + 对应功能点的 PRD，然后从交接文档记录的"下一步"继续。

> 🎯 **检验标准**：新会话的 AI 在 5 分钟内能复述"这个项目在做什么、做到哪了、下一步做什么、有什么坑"。能，交接就成功了。

## 8. 速查：AI 协作检查清单

每次会话前后，逐项过一遍：

**会话开始前：**
- [ ] 开场白含身份 + 文档引用 + 单一任务 + 约束
- [ ] 任务粒度是一个功能点
- [ ] 让 AI 复述需求确认理解

**会话进行中：**
- [ ] 一次一个功能点，测试先行
- [ ] 每步让 AI 汇报，不要一口气做完
- [ ] AI 提议越界 → 拒绝 + 记待办池

**会话结束前：**
- [ ] 跑测试（含金标准回归）
- [ ] 实际运行一次端到端命令
- [ ] Review diff（范围 / 命名 / 位置 / 越界 / 凭据）
- [ ] `git commit`
- [ ] 更新交接文档
- [ ] 上下文快满了 / 换模块 → 开新会话
