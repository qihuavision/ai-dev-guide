# 架构检查清单

> 架构阶段（Phase 1）专用。在动手写核心代码前逐项打勾确认。
> 目标：让"系统怎么组织"在写第一行业务代码前就清晰、可追溯。

## 一、架构产出物

- [ ] **架构设计文档已输出**——`docs/architecture.md` 已完成，包含整体架构图与说明。没有架构文档，AI 写出的代码会各模块风格不一、难以整合。
- [ ] **关键 ADR 已记录**——重要技术决策已用 ADR（Architecture Decision Record）格式记录在 `docs/adr/` 下，每条包含背景、方案、取舍、后果。决策无记录会导致团队/AI 反复推翻重来。
- [ ] **技术选型理由已写明**——框架/库/存储/部署方式的选择附上"为什么选它、对比了哪些替代方案"。只写结论不写理由，后续无法判断是否仍然成立。

## 二、模块与职责

- [ ] **模块划分遵循单一职责**——每个模块/包只做一件事，职责边界清晰、命名能反映其功能。职责混乱的模块必然产生循环依赖和测试困难。
- [ ] **核心模块清单已列出**——文档中列出全部一级模块及其一句话职责说明。模块清单缺失意味着架构还在脑子里，没真正落地。
- [ ] **公共能力已沉淀**——日志、配置、错误处理、时间、ID 生成等横切关注点有统一的公共模块。散落在各处会导致风格不一致和重复代码。

## 三、结构与依赖

- [ ] **目录结构已确定**——`docs/architecture.md` 中给出标准目录树及各目录用途（可参考 `examples/项目骨架结构.md`）。目录乱则文件找不到，AI 也会放错位置。
- [ ] **依赖关系图已画**——用图或表格说明模块间调用/依赖方向，明确"谁可以依赖谁"。无依赖图极易出现循环依赖和分层倒置。
- [ ] **分层方向已约束**——明确禁止反向依赖（如业务层不得调用接口层、核心不得依赖具体实现）。约束缺失会让分层形同虚设。
- [ ] **第三方依赖清单已整理**——列出直接依赖及其用途、许可证、维护状态。不知名的依赖会引入安全和维护风险。

## 四、数据与存储

- [ ] **数据存储设计已出（如需要）**——若项目涉及持久化，已完成表/集合/文件结构设计，含主键、索引、关键字段。无数据设计的项目会在数据层反复返工。
- [ ] **数据流已说明**——数据从输入到存储到输出的流转路径已描述清楚。数据流不清会导致字段丢失、格式不一致。
- [ ] **迁移/初始化方案已考虑（如需要）**——若涉及数据库，已规划 schema 初始化与变更迁移方式。临到上线才想迁移方案极易造成数据丢失。

## 五、安全与可靠性

- [ ] **安全设计已出（如需要）**——认证、授权、凭据管理、敏感数据处理方案已在架构文档中体现。安全留到上线前补往往来不及。
- [ ] **可测试性已考虑**——模块设计支持依赖注入或接口隔离，便于编写单元测试。不可测试的代码会迅速腐化。
- [ ] **错误处理与降级策略已定**——外部依赖失败、超时、部分故障时的行为有统一约定。未约定的错误处理会让系统在异常时行为不可预测。

## 六、扩展与演进

- [ ] **扩展性已预留**——对"可能增长"的点（并发、数据量、新功能接入）有预留接口或说明取舍。一点不留扩展空间，未来改动会伤筋动骨。
- [ ] **配置与代码已分离**——环境相关参数（URL、密钥、阈值）通过配置注入而非硬编码。硬编码会让部署到不同环境时必须改代码。
- [ ] **可观测性已规划**——日志级别、关键指标（metrics）、健康检查端点已在架构中定义。无可观测性则线上问题无从排查。

---

**完成判定**：以上全部勾选后，方可进入实现阶段（写核心代码）。
若某项标注"如需要"且本项目确实不涉及，可勾选并在后面注明 `N/A：本项目不涉及XXX`。
