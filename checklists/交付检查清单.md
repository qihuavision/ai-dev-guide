# 交付检查清单

> 交付上线阶段专用。在打 tag、发布、移交维护方之前逐项打勾确认。
> 任一项未通过都不应宣布"交付完成"。

## 一、文档齐全

- [ ] **立项书已完成并归档**——`docs/proposal.md` 存在且内容完整（背景/目标/范围/风险）。无立项书的交付无法回答"当初为什么做这个"。
- [ ] **PRD / 需求文档已定稿**——`docs/prd.md` 或需求清单已与需求方确认签字。需求未定稿的"交付"会陷入"还差一点"的无底洞。
- [ ] **架构文档已完成**——`docs/architecture.md` 与 ADR 已更新到最终状态。交付时的架构若与代码不符，接手者会被误导。
- [ ] **安全文档已产出**——已完成《安全检查清单》并通过。安全未评审通过的产物不应上线。
- [ ] **测试文档已产出**——测试计划、用例清单、回归基线已归档。无测试文档则后续无法判断"改了有没有破坏旧功能"。
- [ ] **交接文档已更新**——`docs/handover.md` 含部署方式、日常运维、常见故障处理、联系人。无交接文档的交付等于把烂摊子扔给下一个倒霉蛋。

## 二、可运行性

- [ ] **Sprint1 可运行里程碑已达成**——从零起，按文档能在新环境跑通核心流程。跑不通的"完成"只是假象。
- [ ] **README 已就绪**——项目简介、依赖、安装、运行、常见命令一目了然，新人 10 分钟内能跑起来。README 是项目的第一张脸。
- [ ] **安装/初始化脚本已提供**——`scripts/` 下有一键安装或初始化脚本（含依赖安装、配置生成、数据初始化）。手工步骤越多越容易出错。
- [ ] **配置示例已提供**——提供 `.env.example` 或 `config.example.*`，列出全部配置项及说明。没有示例，接手者不知道要配什么。
- [ ] **CHANGELOG 已更新**——本次交付包含的变更、新增、修复、破坏性改动已记入 CHANGELOG。无变更日志则使用者不知道升级会带来什么影响。

## 三、测试与质量

- [ ] **测试全部通过**——单元测试、集成测试 100% 通过，无跳过、无已知失败。带失败跑过的测试套件等于没有测试。
- [ ] **Golden 回归已通过**——核心场景的 golden 用例（期望输出基线）比对一致。golden 测试是防止"悄悄改坏输出"的最有效手段。
- [ ] **关键路径已覆盖**——核心业务路径有自动化测试覆盖，覆盖率达标或已说明取舍。核心路径无测试就是裸奔。
- [ ] **手动冒烟已执行**——按交付场景手工跑过一遍主流程并确认结果。自动化测不到的"整体感觉"需要人来确认。

## 四、安全与稳定

- [ ] **安全评审已通过**——《安全检查清单》全部高危项 ✅，非高危项有处置计划。安全是上线的前置条件，不是优化项。
- [ ] **回滚预案已就绪**——明确的回滚步骤、回滚判断标准、责任人已写入文档。没有回滚预案的上线，一旦出事只能现场抓瞎。
- [ ] **监控告警已就绪**——关键指标（错误率、延迟、资源占用）有监控，异常有告警通道。无监控等于盲飞，出了事只能等用户投诉。
- [ ] **数据已备份**（如涉及）——持久化数据有备份策略且验证过可恢复。没验证过恢复的备份等于没有备份。

## 五、一致性与发布

- [ ] **文档与代码一致**——README、架构文档、接口文档与实际代码/行为一致，无过期描述。过期文档比没有文档更危险，因为它骗人。
- [ ] **版本号已打 tag**——已按版本规范打 Git tag（如 `v1.0.0`），tag 信息含变更摘要。无 tag 则"哪个版本上线了"永远说不清。
- [ ] **依赖已锁定**——`requirements.txt` / `package-lock.json` 等锁文件已提交，构建可复现。不锁依赖的构建在不同时间结果可能不同。
- [ ] **遗留问题已登记**——已知缺陷、TODO、待优化项已记入 issue 列表并排定优先级。不登记的遗留问题会被永久遗忘，直到爆炸。

---

**完成判定**：以上全部勾选后，方可宣布交付完成并对外发布。
建议由非主开发人员（如另一角色或独立 AI 会话）做最终复核，避免"自己查自己"的盲区。
