# 立项检查清单

> 立项阶段（Phase 0）专用。逐项打勾确认，未完成不应进入架构阶段。
> 建议由产品负责人与 AI 协作填写，每项保留简要证据或链接。

## 一、三个灵魂问题

- [ ] **"给谁用"已答清**——明确目标用户画像，越具体越好（"财务部门的报销审核员"优于"公司员工"）。回答模糊会让后续所有需求偏离方向。
- [ ] **"解决什么痛"已答清**——用一句话描述用户现状中的痛点，最好附带可量化的代价（如"每月人均浪费 4 小时手工核对"）。无痛点的项目大概率没有真实价值。
- [ ] **"不做什么"已答清**——明确列出本期不解决的问题和不做的事。范围边界比功能列表更重要，是控制项目膨胀的第一道闸门。

## 二、立项书 6 部分

- [ ] **背景与动机**已写——回答"为什么是现在做"，包含触发事件或业务压力。缺失动机的项目容易在遇到困难时被放弃。
- [ ] **目标与范围**已写——包含本期要交付的核心成果。无目标则无法判断何时算"做完了"。
- [ ] **用户与场景**已写——描述典型用户在什么场景下使用，最好附 1-2 个用户故事。场景缺失会导致功能设计脱离实际。
- [ ] **技术方案概述**已写——说明大致采用的技术栈、关键依赖、是否有现成方案可复用。留白会让 AI 任意发挥，后续返工成本高。
- [ ] **里程碑与时间**已写——至少包含 Sprint1 可运行里程碑和预期交付时间。无里程碑则无法跟踪进度。
- [ ] **风险与开放问题**已写——列出已知风险和尚未明确的问题，并指定跟进人。开放问题不记录会一直悬而未决。

## 三、范围管理

- [ ] **"不做"清单已明确**——以独立小节列出本期明确排除的功能/集成/平台，并与利益相关方对齐。这是防止范围蔓延的核心手段。
- [ ] **范围变更流程已约定**——约定谁有权追加范围、追加需走什么记录流程。无流程则任何人都能随时塞需求。

## 四、目标质量

- [ ] **目标符合 SMART**——每条目标可被 Specific（具体）、Measurable（可衡量）、Achievable（可达成）、Relevant（相关）、Time-bound（有时限）检验。不可衡量的目标等于没目标。
- [ ] **成功标准可验收**——目标能用客观数据或可演示行为验收（如"接口 P95 < 200ms""支持 50 并发不报错"）。无法验收的目标在交付时会扯皮。

## 五、用户与技术

- [ ] **用户角色已定义**——列出全部角色及其权限/职责差异（如"管理员 / 普通用户 / 只读访客"）。角色不清会导致权限和数据隔离设计错误。
- [ ] **技术约束已定**——明确语言版本、运行环境、禁止使用的技术、必须兼容的旧系统等约束。约束不清会让 AI 选出无法落地的方案。
- [ ] **非功能需求已识别**——性能、可用性、合规、数据量级等非功能需求至少有量级估计。忽略非功能需求是项目后期返工的高频原因。

## 六、风险与确认

- [ ] **关键风险已识别**——至少列出 3 条最高风险及对应应对策略（规避/转移/缓解/接受）。未识别的风险会在最坏时机爆发。
- [ ] **立项书已评审并签字**——关键干系人（产品、技术、需求方）已读确认。未评审的立项书只是一份草稿，不具备约束力。

---

**完成判定**：以上全部勾选后，方可进入架构阶段。
