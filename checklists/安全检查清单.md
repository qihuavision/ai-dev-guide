# 安全检查清单

> 通用安全检查清单，适用于所有项目。建议在每个 Sprint 末和交付前各执行一次。
> 标注 ⚠️ 的为高危项，未通过**禁止上线**。
> 用表格逐项打勾，"状态"列填 ✅ 通过 / ⚠️ 待修 / ➖ 不适用。

## 一、凭据与密钥（高危）

| 状态 | 检查项 | 为什么重要 |
|------|--------|----------|
| - [ ] | ⚠️ **凭据未明文存储**——API Key、密码、Token、私钥绝不硬编码在代码或配置文件中，统一走环境变量/Secret 管理 | 明文凭据一旦提交到仓库即永久泄露，即使删除也能从历史找回 |
| - [ ] | ⚠️ **凭据未进入版本库**——`.gitignore` 已覆盖 `.env`、密钥文件；仓库历史中无私密信息（可做 secret 扫描确认） | 一次 `git push` 就能让密钥扩散到所有协作者甚至公网 |
| - [ ] | ⚠️ **凭据有轮换机制**——关键凭据可被更换，且更换不影响系统运行 | 不可轮换的凭据一旦疑似泄露只能"祈祷"没人用 |
| - [ ] | ⚠️ **错误信息不泄露凭据**——异常日志、报错页、调试输出中不会打印完整 Token/密码 | 日志和报错常被多方可见，是凭据泄露的高频通道 |

## 二、权限与访问控制（高危）

| 状态 | 检查项 | 为什么重要 |
|------|--------|----------|
| - [ ] | ⚠️ **最小权限账号**——程序使用的账号/Token 仅授予完成任务所需的最小权限，禁用通配符或超管权限 | 最小权限把"一旦被攻破"的爆炸半径限制到最小 |
| - [ ] | ⚠️ **操作白名单已定义**——对可执行命令/可访问资源/可写入路径有显式白名单，默认拒绝 | 黑名单思路永远漏，白名单"未明确允许即禁止"才安全 |
| - [ ] | 危险操作有审批流——删除、批量修改、生产环境写入等操作需二次确认或审批 | 审批流是误操作和恶意操作的最后一道闸门 |
| - [ ] | 鉴权与授权已分离——"你是谁"（认证）和"你能做什么"（授权）分开实现且都已覆盖 | 只认证不授权等于大门敞开后随便逛 |

## 三、执行与操作安全（高危）

| 状态 | 检查项 | 为什么重要 |
|------|--------|----------|
| - [ ] | ⚠️ **dry-run 模式已实现**——危险操作支持先预览将要发生的变化而不真正执行 | dry-run 能在真正破坏前发现"以为对其实错"的问题 |
| - [ ] | ⚠️ **关键操作有审计日志**——谁、何时、做了什么、结果如何，被完整记录且日志不可被当事人篡改 | 无审计则事故无法追溯、责任无法界定 |
| - [ ] | 操作可回滚——写入/删除/迁移类操作有对应的撤销或回滚路径 | 不可回滚的操作一旦出错只能人工修复数据 |
| - [ ] | 幂等性已保证——重复执行同一操作不会造成数据错乱 | 网络重试、人工重试是常态，非幂等操作会产生脏数据 |

## 四、输入与数据

| 状态 | 检查项 | 为什么重要 |
|------|--------|----------|
| - [ ] | ⚠️ **输入已做校验**——所有外部输入（用户、API、文件）经过类型/长度/格式/范围校验后再使用 | 输入是注入攻击（SQL/命令/路径穿越）的入口 |
| - [ ] | ⚠️ **敏感数据已脱敏**——日志、导出、展示中对手机号/身份证/邮箱等做掩码处理 | 脱敏不做好，日志库本身就成了隐私泄露源 |
| - [ ] | 输出已做编码——输出到 HTML/Shell/SQL 时按目标上下文转义 | 转义缺失导致 XSS、命令注入、注入类漏洞 |
| - [ ] | 大小与频率已限制——上传文件大小、请求频率、批量操作条数有上限 | 无限制会被超大输入或刷量打垮，甚至被用作攻击放大器 |

## 五、传输与依赖

| 状态 | 检查项 | 为什么重要 |
|------|--------|----------|
| - [ ] | ⚠️ **HTTPS / 加密传输**——对外通信强制加密通道，证书有效且禁用弱协议版本 | 明文传输在任何一个网络节点都能被窃听和篡改 |
| - [ ] | ⚠️ **依赖无已知漏洞**——已运行依赖扫描（如 `pip-audit`/`npm audit`/ Dependabot），高危 CVE 已修复或评估 | 你引入的第三方库的漏洞就是你的漏洞，且最容易被自动化攻击扫到 |
| - [ ] | 依赖来源可信——包来源限定官方源或私有源，锁文件已提交 | 不可信来源可能投毒，无锁文件则每次构建版本漂移 |
| - [ ] | 网络隔离已配置（如需要）——服务仅暴露必要端口，数据库/内部服务不直接对公网开放 | 默认全开放等于把内网资产直接摆上货架 |

## 六、其他

| 状态 | 检查项 | 为什么重要 |
|------|--------|----------|
| - [ ] | 依赖供应链已最小化——未引入实际用不到的依赖，移除了未使用包 | 多一个依赖就多一个潜在漏洞面 |
| - [ ] | 安全相关配置有默认安全值——超时、重试、密码强度等默认值就是安全的 | 用户不会改默认值，默认不安全就等于不安全 |
| - [ ] | 已进行一次威胁建模——至少识别出系统的信任边界和主要攻击面 | 没想过的攻击面永远不会被防护 |

---

**判定规则**：
- 所有 ⚠️ 高危项必须为 ✅，否则禁止上线。
- 非 ⚠️ 项标记为 ⚠️ 待修时，需在交付评审中说明缓解措施和修复计划。
- 标记 ➖ 不适用 时必须在后面写明原因，不可默认略过。
